## 1. 产品定位与需求假设

Private Memo 是一款便携的端侧 AI 语音备忘录设备，目标是本地保存录音、默认本地转写与加密，并允许用户显式选择 Wi-Fi 第三方语音 Provider；设备通过手机钱包提交密文和恢复记录。优先级为隐私、防丢失、使用便利。

早期构想包含本地伴聊、TTS、数字分身和原始音频永久备份。当前主线收敛到语音备忘录与加密转写文本恢复；这些扩展不能作为已经交付的功能，也不进入首版验收依赖。

| 目标人群 | 待验证需求 | 验证方法 |
| :--- | :--- | :--- |
| 隐私敏感的加密用户 | 希望记录与解密权限由自己掌握 | 观察是否理解钱包配对、是否能独立完成恢复 |
| 深度记录者、日记与灵感用户 | 希望随时记录，减少账号和服务生命周期依赖 | 比较手机备忘录、录音笔与本设备的真实使用频率 |
| 涉及保密资料的专业用户 | 希望语音转写在本地完成 | 使用其允许测试的样本验证质量、离线可用性和导出需求 |
| 长期记忆保存用户 | 希望设备丢失后仍能找回记录 | 进行模拟丢机、换设备和原钱包恢复任务 |

尚无足够用户研究证明上述人群愿意支付硬件溢价。数字遗产、情感陪伴和数据授权属于长期机会假设，不能直接计入首版市场规模。

## 2. 竞品、差异与护城河

原资料将 PLAUD、Limitless、Friend 作为录音、AI 笔记与陪伴类产品参照。其当时的商业形态可帮助提出假设，但本次整理不核实最新售价、订阅条款、用户规模或存续状态；对外路演前须重查官方来源。

| 比较维度 | 本项目拟验证的差异 |
| :--- | :--- |
| 识别位置 | 语音 ASR 在设备本地运行，断网仍能记录与转写 |
| 内容提交 | 设备先加密，手机钱包提交密文；恢复明文仅在授权浏览器本地显示 |
| 记录归属 | 链上 owner 与配对钱包对应，设备不持有交易私钥 |
| 生命周期 | 尝试降低对专用业务后台的依赖；仍依赖可信页面、钱包和公共 RPC |
| 恢复能力 | 以同钱包恢复实测作为核心标准；不把测试网记录承诺为永久保存 |

硬件外壳、公版模型与“上链”本身不足以构成壁垒。更值得验证的积累包括可审计的数据路径、稳定的跨版本恢复、端侧模型与拾音优化，以及用户可迁移的长期记忆。个人记忆图谱、本地 RAG 和数字分身尚未实现，不作为现有竞争优势。数据可迁移与用户自主导出应优先于人为制造迁移障碍。

## 3. imToken / imKey 生态与商业假设

现有集成面是二维码、钱包 Universal Link、HTTPS DApp 与钱包 provider。钱包承担授权写入和恢复签名；硬件承担记录与本地处理。对 imKey 供应链、安全硬件、渠道的复用属于合作设想，不能据此推定第三方 BLE 协议已开放。

商业模式假设为硬件销售加可选存储或代付服务。原报告的 BOM 35–50 美元、零售 149–199 美元均为早期假设，未计定制 PCB、结构、良率、渠道、售后和认证的完整成本。旧 PPT 的 76.5% 来自 179 美元售价与 42 美元 BOM 的简单测算，不是完整毛利。

不使用“零运维成本”“永久免费”“绝对隐私”等表述。静态页面、RPC、密钥兼容、代付资金和长期数据可获得性均有维护成本或信任边界。

## 4. 硬件方向与工程约束

当前验证方向收敛为 RK3576 8GB，而非同时采购多块高性能开发板。开发板用于获取实际部署、功耗和温度数据；便携最终形态仍需 SoM 或定制 PCB。

| 候选 | 在本项目中的角色 | 仍需证明 |
| :--- | :--- | :--- |
| RK3576 8GB | 首选真板验证方向 | ASR CPU/NPU 路径、可用内存、功耗、温升、冷启动 |
| RK3588 8GB/16GB | 早期完整功能验证备选 | 更高功耗和体积是否值得；不作为当前并行采购要求 |
| Jetson Orin Nano | 早期高性能能力基准参照 | 不作为最终穿戴主板 |
| ESP32-S3、nRF、STM32 等 MCU | 按键、电源、待机与低功耗采集辅助 | 不替代 Linux 主 AI SoC；具体器件按接口与功耗选择 |

便携硬件组合研究包含 2–4 个数字 MEMS 麦克风、音频 Codec、低功耗 MCU、eMMC、PMIC、电池，以及 ATECC608B/SE050 等安全元件候选。具体器件及其密钥派生、AES 和接口支持仍需验证，不等于已集成。

24–48 小时为早期续航目标，尚无真板实测依据。持续运行数瓦级 SoC 与小电池存在冲突，应测量事件触发录音、转写和休眠的实际占空比。首版以按键触发为主；常驻唤醒词、伴聊和 TTS 延后。USB-C、屏幕、背夹与外壳的概念方案见架构设计附录。

## 5. ASR 候选与选择原则

优先确认离线部署与许可可行性，以识别准确率作为产品门槛，再比较资源和工程成本。模型文件尽量控制在约 1GB，但不能按文件体积直接淘汰；必须计入主模型、投影器、VAD、运行时和系统内存。

当前模拟器默认 R2T2；Paraformer 是已有轻量工程基线，SenseVoice 为对照。原资料“Paraformer 已设为默认”的描述仅指更早实验阶段。界面模型切换用于对比，不代表量产型号确定。

| 模型 | 规模/形态 | 主要能力 | 适配判断 | 官方资料 |
| :--- | :--- | :--- | :--- | :--- |
| Paraformer-zh-streaming | 约 220M，流式 | 中文、中英混合、实时识别 | 流式对照候选 | [Sherpa-ONNX 在线 Paraformer](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-paraformer/paraformer-models.html) |
| Zipformer streaming small | 约 14M~几十 MB，int8 | 中文流式识别，低延迟、低资源 | 低功耗对照候选 | [Sherpa-ONNX 在线 Zipformer](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/zipformer-transducer-models.html) |
| SenseVoiceSmall | 约 234M | 中文、粤语、英语、日语、韩语，附带情绪和声音事件标签 | Memo 后处理候选 | [SenseVoice 官方仓库](https://github.com/QwenAudio/SenseVoice) |
| Paraformer-zh-small | 小型离线模型 | 中文录音转写 | 适合录音结束后的批量整理 | [Sherpa-ONNX Paraformer 模型](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/offline-paraformer/paraformer-models.html) |

| Fun-ASR-Nano | 约 800M | 中文、英语、日语及中文方言/口音 | 完整资源与中文效果待目标板验证 | [Sherpa-ONNX FunASR Nano](https://k2-fsa.github.io/sherpa/onnx/funasr-nano/) |

### 核实结论：网易有道 Confucius4-**R2T2**（不是 R2-T2）

检索到的官方产品名是 **Confucius4-R2T2**，缩写 **R2T2** = **R**eal **R**eal-**T**ime **T**ranscription。  
带连字符的 **R2-T2**（[tianyi-lab/R2-T2](https://github.com/tianyi-lab/R2-T2)，[arXiv:2502.20395](https://arxiv.org/abs/2502.20395)）是另一篇 ICML 2025 多模态 MoE 重路由论文，与有道 ASR **无关**。

#### 候选发现是否应覆盖 Open ASR + 中文评测？

**应当两者都覆盖，且角色不同：**

1. **HF Open ASR Leaderboard** — 用于英文/西欧多语的可复现横向对比，以及确认社区是否已提交该家族模型；**不能替代中文离线备忘场景结论**（当前 multilingual 轴不以普通话为主，且 R2T2 本身尚未上榜）。  
2. **中文评测** — 对“中文离线端侧录音备忘”是 **必选项**：至少对齐官方已报的 WenetSpeech / SpeechIO / CN-RealSI，并在目标硬件上自测流式 CER、尾延迟与量化后质量。

**端侧选型提醒（事实边界）**：官方主路径偏 **GPU + vLLM / CUDA GGUF**；端侧更接近 **社区 GGUF + audio.cpp/llama.cpp**，尚无经官方背书的 ONNX/ARM NPU 一体化方案。商用前务必阅读权重许可证中的规模门槛与限制条款。


### 5.2 Meta Seamless Communication 的历史排除结论

本项目暂不纳入 Meta Seamless Communication 系列作为端侧 ASR 或伴聊模型候选。该系列的多语种和语音到语音效果有研究价值，但与当前 **RK3576 8GB、小体积、低功耗、可商用** 的产品约束不匹配：

| 分支 | 调研结论 | 排除原因 |
| :--- | :--- | :--- |
| SeamlessM4T v2 Large | 仅作为服务器/GPU 效果基准 | 2.3B 参数，官方权重文件约 9~11GB；即使只启用 ASR 子模块，也不能据此推断 RK3576 有可接受的峰值内存和实时率 |
| SeamlessStreaming | 不进入端侧候选 | 约 2.5B 参数，主要 checkpoint 约 3.6GB + 4.3GB；流式能力方向正确，但文件、运行时和部署链路都超出当前小硬件预算 |
| SeamlessExpressive | 不进入候选 | 重点是保留韵律/音色的语音到语音翻译，不是本项目所需的本地中文语音备忘录 ASR；模型组合约数 GB，且需要额外申请并接受专用许可/AUP |
| UnitY-Small / UnitY-Small-S2T | 暂不进入中文主路线 | 官方端侧文件约 783MB / 504MB，资源方向较合适，但官方语言集合不含中文，无法替代当前中文录音识别需求 |

许可也是排除条件：M4T 与 SeamlessStreaming 权重采用 **CC-BY-NC-4.0**，Expressive 还受 Seamless 专用许可和 AUP 约束，不能直接作为当前商用硬件产品的默认模型。这里的结论不是“文件超过 1GB 就一律淘汰”，而是综合考虑模型运行时、目标板部署路径、中文能力和商业授权后作出的产品决策。

后续只有在出现同时满足 **中文支持、明确的商业授权、可导出到 RKNN/CPU 端侧运行时、并通过 RK3576 峰值内存/RTF/功耗实测** 的轻量版本时，才重新开启评估。当前资源集中到 R2T2、Paraformer、SenseVoiceSmall、Zipformer 等更贴合本项目的候选。

### 5.3 同一测试集与真板验收

用项目自有人工标注录音覆盖普通话、方言、中英混说、专有名词、金额、日期、噪声、远场、静音和长录音。分别比较中文 CER、英文 WER、漏句/插入错误和关键实体准确率；流式首字、已提交文本和离线终稿分别评价。

## 6. 本地实测证据

### 6.1 R2T2 完整资源实测（2026-09-26）

> 日期：2026-09-26。目的：验证 R2T2 的完整 GGUF 组件、ARM64 可运行性和运行时资源，不以模型文件大小代替硬件判断。

#### 结论

R2T2 不应因完整文件超过 1GB 被排除。官方 Q4 主模型与 Q8 音频投影器合计约 1.36GiB；在 Apple M1 Pro 上使用 4K 上下文时，最大 RSS 约 2.05GB，稳定处理 6.74 秒音频约 0.385 秒。它值得进入 RK3576 8GB 真板测试。

这不是 RK3576 的性能承诺。Apple Metal 与 RK3576 CPU/NPU 的算力、内存分配和功耗不同；目前未确认 R2T2 的官方 RKNN/ONNX/NPU 路径。

#### 测试环境

| 项目 | 配置 |
| :--- | :--- |
| 主机 | MacBook Pro 18,3；Apple M1 Pro；10 核；32GB 统一内存 |
| 模型 | `Confucius4-R2T2-Q4_K_M.gguf`，1,107,404,736 字节 |
| 音频投影器 | `mmproj-Confucius4-R2T2-Q8_0.gguf`，348,336,544 字节 |
| 文件合计 | 1,455,741,280 字节，约 1.36GiB |
| 文件校验 | SHA-256 与 Hugging Face LFS 元数据一致 |
| 运行时 | 官方仓库指定 llama.cpp commit `ad6c66839af3c5646fba8c6c2e2087a1e4e38948` |
| 构建 | macOS arm64，AppleClang，Accelerate + Metal；Python 3.12 native extension |
| 音频 | 官方 `resources/test.wav`，单声道 16kHz，6.74 秒 |
| 输出 | `之前有顾客自己带酒水，也没加收钱或者不让喝。` |

官方仓库预编译包仅支持 Linux x86_64/CUDA。本次从官方指定提交重新编译 ARM64 后端，证明源码路径能在 ARM64 运行；没有修改模型或推理逻辑。

#### 结果

| 配置 | 加载 | 推理 | RTF | 最大 RSS | macOS peak footprint |
| :--- | ---: | ---: | ---: | ---: | ---: |
| Metal，32K ctx / 8192 batch，首次编译 | 25.57s | 1.16s | 0.171 | 5.35GB | 4.24GB |
| Metal，4K ctx / 1024 batch | 0.59s | 0.44s | 0.066 | 2.12GB | 0.97GB |
| Metal，4K ctx / 1024 batch，连续三轮 | 1.88s | 0.505 / 0.386 / 0.385s | 稳定约 0.057 | 2.05GB | 0.96GB |
| CPU-only，4K ctx / 1024 batch | 1.23s | 0.92s | 0.137 | 2.22GB | 1.08GB |
| Metal，2K ctx / 512 batch | 1.46s | 0.55s | 0.082 | 1.83GB | 0.73GB |
| OrbStack Ubuntu ARM64 CPU，2K / 512，连续三轮 | 2.68s | 1.648 / 0.938 / 0.907s | 稳定约 0.135 | 3.06GB | Linux 未测此指标 |

RSS 包含文件映射和共享页，在统一内存系统上不能直接当作独占物理内存；`peak footprint` 更接近 macOS 对进程实际内存压力的估计。RK3576 Linux 上应使用 PSS、CMA/NPU 分配和整机 `MemAvailable` 联合判断，不能直接复制以上数值。

#### 判断

1. 默认 32K 上下文浪费约 3GB RSS。语音备忘的短句转写优先采用 2K/4K 上下文，并用长录音验证是否溢出。
2. Q4 主模型不是“几百 MB”；约 348MB 指的是 `mmproj-Q8`。但完整 1.36GiB 组合在 8GB 级设备上仍有验证价值。
3. 4K 配置的本地数据表明 ASR 单模型资源可控。按项目已有实测，Paraformer+VAD 约 204MB RSS、0.6B LLM 加载峰值约 1.07GB；粗略相加仍不能代替整链路并发测试，但没有出现必然超过 8GB 的证据。
4. R2T2 当前最大的工程风险是 RK3576 缺少已确认的 NPU 部署路径。CPU 基线必须先上真板；若 RTF、功耗或温度不合格，再决定是否投入 RKNN 转换。
5. 这里只验证一段官方音频，不能据此判断准确率领先。下一步必须使用项目自有普通话、方言、中英混说、噪声、金额和专有名词测试集。

#### 真板验收

RK3576 8GB 至少测试 2K/512 与 4K/1024 两组配置，分别记录冷/热启动、连续 10 次 RTF、P95 延迟、进程 PSS、整机可用内存、CPU/NPU 利用率、平均/峰值功耗、温升和降频。与 Paraformer-small、SenseVoice int8 使用相同音频、VAD 边界和指标对比后再决定默认模型。

完整环境和复测命令见 [项目 README 的 R2T2 复测章节](../../README.md#7-r2t2-本地复测)。脚本要求先按 R2T2 官方仓库说明编译 `qwen3asr_native`，并通过 `DYLD_LIBRARY_PATH`（macOS）或 `LD_LIBRARY_PATH`（Linux）提供对应的 llama.cpp 动态库。

**结论**

### 6.4 Android 断网真机实验（2026-10-15）

在尚无 RK3576 开发板的情况下，使用 Solana Mobile Seeker（MT6878、Android 15、arm64、系统内存 7,841,644,544 字节）验证完整移动端软件链。应用未申请 `INTERNET` 权限，实验期间飞行模式开启且 `active_network=false`。三套模型经 USB 复制后与主机 SHA-256 一致。

统一 6.74s 样本、4 CPU 线程、每模型 3 轮：

| 模型 | 冷加载 | 推理中位数 | RTF 中位数 | 最大 PSS | 输出与失败 |
| :--- | ---: | ---: | ---: | ---: | :--- |
| Paraformer int8 | 2.17s | 94ms | 0.014 | 245,402KiB | 语义正确，0/3 失败 |

普通话、中英混说、四川方言和 8kHz 厂商样本共 12 次推理零运行失败；这是兼容性与明显退化检查，不是独立 CER/WER 评测。5 秒纯静音经 Silero VAD 后无文本，语音–静音–语音样本得到两段。真机麦克风录得 4.60s、16kHz、单声道、16-bit WAV（RMS -30.9dBFS），VAD 后完成 Paraformer 转写。AES-256-GCM/HKDF、篡改拒绝和二维码编解码在 Android 通过，并由既有 Python 实现完成反向解密、逐字节重加密和摘要交叉验证。

该实验把“能否在约 8GB arm64 移动设备上完整运行”从未知变为已验证，同时显示 R2T2 的内存约为轻量模型的一个数量级、速度仍达到 RTF<1。它没有测量整机功耗、续航、长时间温升和降频，也没有覆盖 RK3576、RKNN/NPU、GPIO、目标屏幕、MEMS 阵列或真实钱包交易，因此默认模型与目标硬件选型仍须等待独立标注集和 RK3576 真板数据。原始结果与构建说明见 [`lab/android/`](../../lab/android/README.md)。

## 10. 钱包配对网页安全复核（2026-10-16）

在线地址 `https://ai-hardware-gamma.vercel.app/` 当日返回的仍是旧版单文件页面：`/qrcode.js` 为 HTTP 404，页面只生成明文配对凭据，没有二维码容器。这是签名两次后没有二维码的直接原因。发布源位于 `web3/app/`，可上传的完整静态快照由 `web3/tools/make_deploy_bundle.sh` 生成到 `web3/dist-page/`；Vercel 必须重新部署整个目录，不能只替换 `index.html`。

安全边界与结论：

1. 配对载荷位于 URL fragment（`#k=`）中，按浏览器协议不会随 HTTP 请求或 Referer 发给 Vercel。页面没有第三方脚本、分析 SDK、Cookie 或 Web Storage；签名与 HKDF 派生均在 imToken DApp WebView 本地完成，签名不广播、不上链。
2. 配对凭据当前直接包含 `owner`、方案标识和 32 字节 KEK。获得二维码、明文、截图或剪贴板内容的人可以解密受该 KEK 保护的记录，所以它只能作为实验配对方案，不能当作普通登录二维码传播。新版以相机扫码为主，移除了系统分享入口，明文复制收进带警告的回退区。
3. 托管页面本身是信任边界：Vercel 项目账号、域名或下一次部署若被控制，恶意 JavaScript 可以读取钱包返回的签名和派生 KEK。量产前应改为设备发起、短时有效、一次性的加密握手，并建立代码审查、固定发布版本、部署审计和账号多因素认证。
4. 当日在线响应只有 HSTS，缺少 CSP、`nosniff`、`Referrer-Policy`、`Permissions-Policy` 与防嵌入策略。新版 `vercel.json` 已补齐这些响应头，JavaScript 已移出内联块；部署后须再次从公网检查响应头。
5. 页面仍允许用户配置 HTTPS RPC。RPC 会看到客户端 IP、链查询方法、合约及地址，但不应收到 KEK、助记词或解密后的正文。不要填写不可信 RPC，也不要把助记词输入来源不明或未核对版本的页面。

当前风险评级为**实验可用、量产不可用**。主要剩余风险是二维码内含可长期使用的 KEK，以及托管 JavaScript 可接触签名派生过程；安全响应头只能降低网页注入与嵌入风险，不能消除这两项架构风险。

## 11. 签名配对与上链是否必须依赖 Vercel（2026-10-16）

### 11.1 结论

**不必须使用 Vercel；本项目确定继续使用公共静态网页。** 当前实现选择 Vercel，是因为 imToken DApp Browser 会向其打开的 DApp 网页注入 EIP-1193 Provider，网页可据此调用 `eth_requestAccounts`、`eth_signTypedData_v4` 和 `eth_sendTransaction`。Vercel在这里仅提供公开 HTTPS 静态文件，不参与密钥派生、签名或交易广播协议。

需要区分两层：

- 继续使用 imToken **内置 DApp Browser + 注入 Provider** 时，需要一个 imToken 能打开的可信 HTTPS 页面，但可以部署在自有域名、Cloudflare Pages、Netlify、GitHub Pages、对象存储/CDN 等位置，并不绑定 Vercel。
- 技术上可用 WalletConnect v2 取消网页，但本项目不采用：连接稳定性、SDK 集成、持续升级、Project ID 和 Relay 依赖均增加不可控风险。

### 11.2 可选路径比较

| 路径 | 是否需要网页 | 是否依赖联网服务 | 配对签名返回 | 上链 | 评价 |
| :--- | :---: | :---: | :--- | :--- | :--- |
| 当前 imToken DApp Browser | 是 | 静态 HTTPS 托管、钱包/RPC | 网页生成 KEK 二维码，硬件再扫描 | 网页调用钱包 Provider | MVP 已跑通，改动最小；网页代码是高信任边界 |
| 更换静态托管商 | 是 | 任意可信 HTTPS 托管、钱包/RPC | 与当前相同 | 与当前相同 | 可消除 Vercel 厂商绑定，但不消除网页风险 |
| 硬件 App 集成 WalletConnect v2 | 否 | WalletConnect Relay、钱包/RPC | 加密会话直接返回硬件，无需回扫 KEK 二维码 | 会话请求 `eth_sendTransaction` | **不采用**；稳定性、SDK 与持续升级风险不可控 |
| `ethereum:` / ERC-681 交易二维码 | 否 | 钱包/RPC | 不支持当前 EIP-712 双签名回传 | 理论上可表达部分合约调用 | 只能覆盖部分上链场景，不能独立完成当前配对协议 |
| imToken DApp 深链 | 仍需要 | HTTPS 页面、钱包/RPC | 由被打开页面处理 | 由页面处理 | 深链只是打开 DApp URL，不是签名协议替代品 |
| 设备持有链上私钥并自行签名 | 否 | RPC | 无需 imToken 配对 | 设备自行广播 | 改变非托管钱包边界与密钥责任，不符合当前方案 |

EIP-712只定义结构化数据的编码与签名，不定义跨设备传输；EIP-1193只定义 DApp 向钱包发 RPC 请求的 Provider 接口。ERC-681定义的是交易请求 URL，不能把当前两次 `eth_signTypedData_v4` 的返回值送回硬件。因此，去掉网页时仍须由 WalletConnect 或自研通信协议承担请求与响应传输，不能仅把现有网页 URL 换成普通交易二维码。

### 11.3 对本项目的建议

1. **静态网页是正式产品路径。** 所有设备共用同一个自有域名；硬件二维码只引用该域名，不写死 Vercel、Cloudflare 等托管商域名。
2. **采用版本化且向后兼容的 URL。** 量产设备使用类似 `https://wallet.example.com/v1/#...` 的路径；已经售出的版本长期保留，只为新协议增加 `/v2/`，不直接覆盖旧协议行为。
3. **准备双托管和 DNS 切换。** 主、备平台部署同一构建产物并核对 SHA-256；域名 DNS 保持可切换，定期演练主站故障后的恢复。用户和固件始终访问自有域名。
4. **收紧发布与域名权限。** 域名注册商锁、DNSSEC（提供商支持时）、账号 MFA、独立部署账号、最小权限、双人发布复核、部署日志和可回滚版本均进入量产门槛。
5. **网页保持纯静态和无追踪。** 不引入分析 SDK、广告、第三方脚本、远程字体或动态后端；继续使用 CSP、禁止嵌入、无 Referer，并监控首页及关键资源的可用性和内容哈希。
6. **明确长期服务承诺。** 静态页面与域名是所有已售设备的共同基础设施，须纳入产品支持周期、停服预案和源码/部署凭据交接，不以某个免费托管套餐的存续作为保障。

主要依据：[imToken DApp SDK](https://docs.token.im/dapp-sdk/en/)说明 DApp Browser 向网页提供 Provider，并明确原生 App/普通浏览器可通过 WalletConnect 连接 imToken；[imToken WalletConnect v2 指南](https://support.token.im/hc/en-us/articles/20079311809945-imToken-Fully-Supports-WalletConnect-2-0-User-Guide-Important-Notices)确认扫码与 Deep Link 两种连接方式；[WalletConnect Sign API](https://github.com/WalletConnect/walletconnect-docs/blob/main/docs/api/sign/wallet-usage.md)定义钱包与 DApp 之间可承载消息和交易签名请求的会话；[EIP-1193](https://eips.ethereum.org/EIPS/eip-1193)、[EIP-712](https://eips.ethereum.org/EIPS/eip-712)与[ERC-681](https://eips.ethereum.org/EIPS/eip-681)分别界定 Provider、结构化签名和交易请求 URL 的能力边界。
